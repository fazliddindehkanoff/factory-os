Ты — старший инженер по качеству и надёжности. Проект **Factory OS** — многотенантная платформа снабжения и согласований (Telegram-бот + Telegram Mini App + backend). Стек: TypeScript / Express · PostgreSQL (Drizzle ORM) · grammY · React + Vite (`web/`). Корень: `~/factory-os`.

Правила на весь прогон:
- **Прод не трогать.** Вся работа — на локальной копии.
- Активная ветка — `main` (см. README). Папку `factory-os-master/` и `photo_*.jpg` игнорировать (легаси-артефакты).
- Тесты идут на pglite (in-memory Postgres), ~15 s на файл — это нормально, не считай медленность ошибкой.
- Пиши по-русски, отчёты — с таблицами.
- Ничего не удаляй и не переписывай, предварительно не прочитав файл.

Выполни **4 фазы строго по порядку**, между фазами показывай результат.

## Фаза 1 — Полный анализ проекта
Изучи архитектуру и дай отчёт:
- Структуру: `src/` (auth, bot, config, db, http, rbac, server, services, workflow), `web/src/`, `drizzle/`, `deploy/`.
- Модель данных: `src/db/schema.ts` (requests, workflowSteps, approvals, signatures, requestStatusHistory, auditLogs, quotations, stockBalances/stockMovements, requestItems, users, userRoles, rolePermissions, permissions).
- RBAC: `src/rbac/{permissions,system-roles,rbac}.ts`.
- Движок workflow: `src/workflow/{engine,step-kinds}.ts`.
- Жизненный цикл: `src/services/{lifecycle,approval,request,warehouse}.service.ts`.
- HTTP-слой: `src/http/{routes,admin.routes,compat.routes,auth.middleware,legacy-auth}.ts`. **Важно:** есть два API-слоя (canonical `routes.ts` при `SERVE_DESIGN=0` по умолчанию; legacy `compat.routes.ts` при `SERVE_DESIGN=1`) и две ветки продвижения заявки (`performAction` и `approveApproval`).
- Фронтенд: `web/src/App.tsx`, `api.ts`, `screens/*`, `admin/*`.
Запусти baseline: `npm run typecheck`, `npm test`, `cd web && npm run build`. Зафиксируй результат.
**Выход фазы 1:** отчёт об архитектуре + baseline тестов.

## Фаза 2 — Функциональное тестирование по ролям
Для каждой из 18 системных ролей (`src/rbac/system-roles.ts`) проверь:
1. **Backend — бизнес-логика.** Корректность роутинга (`applicableSteps`/`nextStep`: границы сумм, inStock, requestType), переходов статусов, расчётов (estimatedAmount, КП), separation of duties, терминальных статусов, идемпотентности склада, откатов транзакций. Найди логические ошибки.
2. **Доступ ролей.** Соответствует ли доступ каждой роли её назначению (не больше/не меньше). Сверь каждый endpoint с требуемым правом; найди роли с избыточными/недостающими правами, мёртвые права (в каталоге есть, нигде не проверяется), рассинхрон canonical vs compat.
3. **Frontend — UI по ролям.** Гейтинг меню/экранов по правам из `/me`; действия по заявке (backend-driven?); валидация форм; навигация; обработка 401/403; соответствие показываемых данных роли.
4. **End-to-end жизненный цикл заявки.** Пройди путь создание → согласование → проверка склада → закупка → оплата → доставка → приёмка → выдача → закрытие. На каждом шаге проверь целостность: `status`↔`currentStepId` согласованы, пишется history+audit, approvals/signatures корректны, склад двигается идемпотентно, при нехватке — откат всей транзакции. Прогони e2e-тесты: `npx vitest run src/services/pilot-golden-path.test.ts src/services/warehouse-lifecycle.test.ts src/http/procurement-lite.test.ts`.
**Выход фазы 2:** таблицы находок (ID, severity CRITICAL/HIGH/MEDIUM/LOW, файл:строка, описание, воспроизведение, ожидалось vs фактически) + карта жизненного цикла + вердикт по каждой роли. Совет: распараллель на под-агентов по 4 направлениям.
