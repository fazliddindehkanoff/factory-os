# Тест-режим: проверка mini app по ролям в нескольких окнах

Режим для QA: **не надо менять роль одному Telegram-номеру**. Seed создаёт отдельных
тестовых пользователей с разными `user_id` и ролями; каждое окно браузера — отдельный
пользователь со своей сессией (токен в `sessionStorage`, не в `localStorage`).

Матрица «кто что видит и какую кнопку может нажать» — [ROLE_MATRIX.md](ROLE_MATRIX.md)
(права) и таблица шагов ниже (статусы).

## Включение

Работает **только** при `NODE_ENV=development` + `ENABLE_DEV_AUTH=1`
(в production сервер с `ENABLE_DEV_AUTH=1` вообще не стартует, а
`/api/auth/dev` и `/api/dev/users` отвечают stealth-404 — панель DEV не рендерится).

```bash
npm run db:migrate
npm run seed:test        # идемпотентный — можно перезапускать
npm run dev              # backend :3100 (или PORT из .env)
```

## Как открыть несколько окон одновременно

URL-параметр `user` пиновывает **это окно** к тестовому пользователю:

```
https://<host>/?user=sklad_01
https://<host>/?user=nach_sklad_01
https://<host>/?user=snab_01
https://<host>/?user=zamdir_01
https://<host>/?user=gendir_01
https://<host>/?user=founder_01
https://<host>/?user=admin_01
```

(`/test?user=...` тоже работает — SPA отдаёт index.html на любой путь.)

Токен кладётся в `sessionStorage`, поэтому 5–7 вкладок/окон одного браузера — это
5–7 независимых пользователей. Инкогнито/другие браузеры не нужны, но тоже работают.

Внутри приложения — плавающая кнопка **DEV** (справа снизу): панель со списком
тестовых пользователей, клик переключает пользователя текущего окна.

## Маршрут заявки (workflow «Тестовый маршрут (полный)»)

| # | Шаг (статус) | Кто действует | Кнопки |
|---|---|---|---|
| 0 | Создание | `sklad_01` | «Новая заявка» |
| 1 | Подтверждение начальника склада (`pending_approval`) | `nach_sklad_01` | Согласовать (PIN) / Отклонить |
| 2 | Закупка: КП и выбор поставщика (`procurement`) | `snab_01` | Добавить КП / Выбрать поставщика / Отклонить |
| 3 | Одобрение зам. директора (`pending_approval`) | `zamdir_01` | Согласовать (PIN) / Отклонить |
| 4 | Одобрение ген. директора (`pending_approval`) | `gendir_01` | Согласовать (PIN) / Отклонить |
| 5 | Утверждение учредителя (`pending_approval`) | `founder_01` | Согласовать (PIN) / Отклонить |
| 6 | Прибытие товара на склад (`delivery`) | `sklad_01` (или `nach_sklad_01`) | Прибыло на склад |
| 7 | Приёмка товара (`receiving`) | `sklad_01` | Принять товар |
| 8 | Подтверждение получения (`close`) | **только автор** (`sklad_01`) | Подтвердить получение |

Терминальные статусы: `closed`, `rejected`, `cancelled` (+ `approved`, `archived`).

Сид сразу кладёт 3 заявки: свежую (шаг 1), «у снабженца» (шаг 2) и отклонённую —
чтобы списки/фильтры/видимость можно было проверять без подготовки.

## Что проверять в каждом окне

- видит ли пользователь заявку в списке/инбоксе (модель видимости: свои + участвует +
  роль в workflow; `requester` — только свои);
- какие кнопки доступны на текущем шаге (и что чужих кнопок НЕТ);
- меняется ли статус у всех окон после действия (автообновление ~30 сек или reload);
- SoD: автор не может согласовать свою заявку; закрыть может только автор;
- PIN: неверный PIN блокируется, верный `1234` проходит.
